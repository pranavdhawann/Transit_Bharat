# Limitations

Honest, current as of the hackathon submission build. Read this before
trusting anything.

## Data honesty

1. **All vehicle movement is synthetic.** Buses on the map are generated by a
   deterministic simulator (`src/lib/vehicles.ts`) as a pure function of
   server time. They are always labeled `DEMO`. No live government or operator
   feed is connected (hackathon rules prohibit unapproved integrations).
2. **Network geometry is real, timetables are not.** Metro lines and bus
   corridors come from official Delhi OTD GTFS snapshots (bus vintage Feb
   2023 via the MobilityData mirror; services in it end 2024-01-01). We use
   real stops and true stop sequences — never as current schedules.
3. **Only 4 bus corridors + metro lines are loaded.** The feed has 2,964
   routes; we ship representative corridors covering the demo anchors to keep
   the graph small, fast and judgeable. The pipeline ingests all of it.
4. **Duration model**: effective speeds per mode + bus dwell (~36 s/stop) +
   central-Delhi traffic factor (0.8× north of lat 28.60) + board waits
   (2.5/3.5 min). Deterministic estimates, not predictions.
5. **Fares are estimates** (flat ₹20 bus; metro distance slabs ₹10–₹60).
6. **Transit legs are emitted as `DEMO`**, never as authoritative `SCHEDULED`
   times, because no live timetable backs them.
7. **AI feature boundary**: `/api/ai/preferences` extracts constraints only
   (OpenAI Responses API with strict schema when a key exists; otherwise a
   transparent heuristic labeled `heuristic`). It cannot plan or alter routes.

## Scope cuts (deliberate)

- Delhi pilot only — no other cities.
- No OTP integration yet: routing runs on the built-in deterministic engine.
  The journeys API response schema is normalized specifically so an
  OpenTripPlanner adapter can be dropped in without UI changes.
- No accounts/login, no payments/ticketing/UPI/NCMC, no SOS, no complaints,
  no crowdsourcing, no occupancy/carbon/gamification features.
- "Arrive by" planning is not implemented ("Leave now" only); the AI parser
  may *note* a deadline but the router does not yet honor it.
- Geolocation is deliberately unused — the demo must be deterministic for
  judging.
- Hindi is a partial beta (key journey strings only); search aliases include
  some Devanagari names. We do not advertise full bilingual support.

## Engineering limitations

- **Disruption state is in-memory** (`globalThis`). It resets on server
  restart/redeploy and is not shared across serverless instances. Auto-expires
  after 30 minutes so demos cannot get stuck.
- **Vehicle simulator granularity**: ping-pong interpolation along stop-to-stop
  straight lines, not road shapes. Positions look plausible but are not
  road-accurate between stops.
- **Router optimality**: Dijkstra over a ~350-node curated-subset graph with
  composite cost profiles. Good on the pilot network; not a general-purpose
  Indian-city router.
- Journey IDs embed a one-minute time bucket; deep links re-plan after the
  bucket rolls over.
- GO-mode "Switch route" after a simulated delay restarts guidance from the
  new itinerary's beginning rather than mid-junction rebalancing.
- Map tiles depend on OpenFreeMap availability (positron fallback, then an
  offline notice); the text timeline remains fully usable by design.

## Accessibility status

Implemented: large touch targets, visible focus states, semantic landmarks,
aria combobox/listbox search pattern, no color-only status meaning (badges
always carry text), `prefers-reduced-motion` respected for map animation and
transitions, keyboard shortcuts documented on-screen in GO mode.

Not done: full screen-reader journey audit, complete Hindi localization.
